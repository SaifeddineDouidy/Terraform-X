\section{Introduction \& Core Principles}
This document is the primary technical guide for the HolisticX cloud infrastructure. It details the Terraform code structure, the multi-environment deployment strategy, and the underlying AWS architecture.

\begin{itemize}
    \item \textbf{Infrastructure as Code (IaC):} All infrastructure is managed by Terraform. \textbf{Do not make manual changes in the AWS Console.}
    \item \textbf{Modularity:} The code is organized into reusable modules to keep it DRY (Don't Repeat Yourself).
    \item \textbf{Environment Isolation:} Each environment (dev, staging, prod) is a completely separate deployment managed by Terraform Workspaces.
\end{itemize}

\section{Project Setup \& Prerequisites}
\begin{guidebox}{Action Required: Configure the Terraform Backend}
Before you can deploy anything, you must configure the remote backend where Terraform will store its state file.
\begin{enumerate}
    \item \textbf{Create an S3 Bucket:} Manually create a private S3 bucket in AWS. A good name is \texttt{holisticx-terraform-state-<your-account-id>}.
    \item \textbf{Update Backend Configuration:} Open \texttt{live/my-project/backend.tf} and update the \texttt{bucket} name.
    \item \textbf{Initialize Terraform:} Run \texttt{terraform init} from \texttt{live/my-project}.
\end{enumerate}
\end{guidebox}

\section{Deep Dive: The \texttt{live/my-project} Directory}
This directory is the "composition root" where the entire infrastructure is assembled. Understanding these files is key to understanding the project.

\subsection{\texttt{main.tf}: The Blueprint}}
This is the most important file. It defines which modules to use and how to connect them. It's like the main blueprint for the entire house. It doesn't contain logic for creating individual resources; instead, it declares module blocks and passes variables to them. For example, it passes the output of the \texttt{network} module (like the VPC ID) as an input to the \texttt{ecs\_fargate} module.

\subsection{\texttt{variables.tf}: The Contract}}
This file defines all the input variables that the root module expects. Think of it as the "contract" for the infrastructure. It defines the name and type of every variable that can be passed in from a \texttt{.tfvars} file (e.g., \texttt{variable "domain\_name" \{ type = string \}}). It also sets default values for optional variables.

\subsection{\texttt{env/*.tfvars}: The Configuration Files}}
These files provide the actual values for the variables defined in \texttt{variables.tf}. You will have one \texttt{.tfvars} file for each environment (e.g., \texttt{develop.tfvars}, \texttt{staging.tfvars}). This is where you specify the differences between environments, such as instance sizes, domain names, and feature flags.

\subsection{\texttt{locals.tf}: The Scratchpad}}
This file is a "scratchpad" for creating intermediate, reusable variables. It takes the raw input from the \texttt{.tfvars} file and transforms it into more useful constructs. Its most important job is to create the \texttt{common\_tags} block that is applied to every resource, ensuring consistent tagging for cost allocation.

\subsection{\texttt{providers.tf}: The Tool Configuration}}
This file configures the "tools" that Terraform uses, in this case, the AWS and PostgreSQL providers. It sets the AWS region and, crucially, defines the \texttt{default\_tags} block, which automatically applies the \texttt{common\_tags} from \texttt{locals.tf} to every single resource the AWS provider creates.

\subsection{\texttt{outputs.tf}: The Results}}
This file defines what information to display after a successful \texttt{terraform apply}. It's used to output important, dynamically generated values like the RDS database endpoint or the Route 53 name servers that you need for manual configuration steps.

\section{Managing Environments with Workspaces}
We use Terraform Workspaces to manage multiple environments. A workspace is an independent state file, allowing you to deploy a full copy of the infrastructure without affecting other environments. The logic in \texttt{locals.tf} translates the workspace name into a standardized \texttt{Environment} tag for all resources.

\section{Deployment Guide}
\subsection{Step 1: Create and Select Your Workspace}
\begin{minted}{bash}
# Run from live/my-project/
cd live/my-project
terraform workspace new <your-workspace-name>
terraform workspace select <your-workspace-name>
\end{minted}

\subsection{Step 2: Create Your Variable File}
Copy an existing \texttt{.tfvars} file and modify it. \textbf{You must provide a globally unique name for the \texttt{rds\_backup\_s3\_bucket\_name} variable.}

\subsection{Step 3: Cost Estimation with Infracost}
\begin{minted}{bash}
# Authenticate with Infracost Cloud (one-time setup)
infracost auth login

# Generate a cost breakdown
infracost breakdown --path . \
  --terraform-var-file="env/<your-var-file>.tfvars" \
  --usage-file="infracost-usage.yml"
\end{minted}

\subsection{Step 4: Plan and Apply}
\begin{minted}{bash}
terraform plan -var-file="env/<your-var-file>.tfvars"
terraform apply -var-file="env/<your-var-file>.tfvars"
\end{minted}

\subsection{Step 5: Post-Deployment DNS}
For the first deployment, you must delegate DNS from your registrar (IONOS) to AWS.
\begin{minted}{bash}
terraform output name_servers
\end{minted}
Log in to IONOS and update the NS records for your domain to these four values.
