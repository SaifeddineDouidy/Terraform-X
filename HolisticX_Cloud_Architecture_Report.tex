\section{Introduction}
This document serves as the primary technical guide for the HolisticX cloud infrastructure. It details the Terraform code structure, explains the multi-environment deployment strategy using Terraform Workspaces, and provides a summary of the underlying AWS architecture. The entire infrastructure is managed as code to ensure consistency, repeatability, and version control.

\section{Project Structure}
The repository is organized into two main directories: \texttt{live} and \texttt{modules}.

\begin{description}
    \item[\texttt{modules/}] This directory contains reusable, modular components that define a specific piece of the architecture (e.g., a VPC, an ECS service, an RDS database). Each module is self-contained and exposes a set of input variables for customization.
    \item[\texttt{live/}] This directory represents the deployable, top-level configuration. It composes the reusable modules from the \texttt{modules/} directory to build the complete infrastructure. The \texttt{live/my-project} directory is the root from which all Terraform commands should be run.
\end{description}

\section{Module-by-Module Breakdown}
\begin{description}
    \item[\texttt{network}] The foundational module. It creates the VPC, all four subnet types (Main Public/Private, Keycloak Public/Private), the Internet Gateway, and the NAT Gateway.
    \item[\texttt{iam}] Defines all necessary IAM roles and policies, including the Task Execution Role (for ECS to pull images) and the Task Role (for application code to access AWS services).
    \item[\texttt{ecr}] Creates a dedicated ECR repository for each microservice defined in the \texttt{.tfvars} file.
    \item[\texttt{rds}] Provisions the main, shared PostgreSQL RDS instance for the application microservices.
    \item[\texttt{ecs\_fargate}] A complex module that creates the main ECS cluster and deploys all application microservices (Spring Gateway, Next.js, etc.) as Fargate services.
    \item[\texttt{keycloak}] A self-contained module that provisions the entire isolated Keycloak stack: its dedicated ALB, ECS cluster, and RDS database.
    \item[\texttt{alb}] Provisions the main Application Load Balancer for the application services.
    \item[\texttt{route53}] Manages the AWS Route 53 Hosted Zone and automatically creates DNS records to point subdomains to the correct load balancers.
    \item[\texttt{waf}] Defines the AWS Web Application Firewall rules, which can be associated with the load balancers.
    \item[\texttt{xray}] Configures AWS X-Ray for distributed tracing.
\end{description}

\section{Multi-Environment Strategy with Terraform Workspaces}
The project is designed to manage multiple environments (e.g., development, staging, production) from a single codebase using **Terraform Workspaces**. Each workspace maintains its own separate state file, ensuring that changes in one environment do not affect another.

\subsection{How it Works}
The logic is defined in \texttt{live/my-project/locals.tf}. The current workspace is identified by \texttt{terraform.workspace}.

\begin{minted}{terraform}
locals {
  // Maps the current workspace name (e.g., "dev-saif") to a 
  // standardized environment tag (e.g., "Dev").
  // Defaults to "Dev" if no mapping is found.
  environment_mapped = lookup(
    var.workspace_to_environment_tag_map, 
    terraform.workspace, 
    "Dev"
  )

  // ...
  
  common_tags = {
    Project     = var.project
    Service     = var.service
    Environment = local.environment_mapped // This tag is used everywhere
  }
}
\end{minted}

This setup allows for both shared and environment-specific configurations.
\begin{itemize}
    \item \textbf{Shared Configuration:} The core infrastructure defined in \texttt{main.tf} is the same for all environments.
    \item \textbf{Environment-Specific Configuration:} You can use different \texttt{.tfvars} files for each environment to specify different instance sizes, VPC CIDRs, or feature flags.
\end{itemize}

\subsection{Step-by-Step Deployment Guide}
Follow these steps to deploy a new environment or update an existing one. All commands should be run from the \texttt{live/my-project/} directory.

\subsubsection{1. Create a New Workspace}
To create a new environment (e.g., for a new feature branch or a staging environment), first create a new workspace.
\begin{minted}{bash}
# Create a new workspace named 'staging'
terraform workspace new staging
\end{minted}
This command creates a new, empty state file for the `staging` environment.

\subsubsection{2. Select the Workspace}
Before running any commands, always ensure you are in the correct workspace.
\begin{minted}{bash}
# List available workspaces
terraform workspace list

# Switch to the 'staging' workspace
terraform workspace select staging
\end{minted}

\subsubsection{3. Prepare a Variable File}
Create a new variable file for your environment, e.g., \texttt{env/staging.tfvars}. You can copy \texttt{env/develop.tfvars} as a starting point and adjust the values as needed (e.g., increase instance sizes, enable Multi-AZ for RDS).

\subsubsection{4. Plan the Deployment}
Always run a \texttt{plan} first. This is a dry run that shows you exactly what changes will be made.
\begin{minted}{bash}
# For the staging environment
terraform plan -var-file="env/staging.tfvars"
\end{minted}
**Review the plan carefully.** Ensure it is creating, modifying, or destroying the resources you expect.

\subsubsection{5. Apply the Changes}
Once you are confident in the plan, apply it.
\begin{minted}{bash}
# For the staging environment
terraform apply -var-file="env/staging.tfvars"
\end{minted}

\subsubsection{6. Post-Deployment: DNS Configuration}
For the very first deployment of a new root domain, you must perform a one-time manual step.
\begin{minted}{bash}
# Get the AWS name servers for your new Route 53 Hosted Zone
terraform output name_servers
\end{minted}
Log in to your domain registrar (IONOS) and update the name server (NS) records for your domain to the four values provided by the output. This delegates DNS control to AWS.

\section{Data & Secrets Layer}
\begin{itemize}
    \item \textbf{Main RDS Instance:} A \texttt{db.t3.micro} PostgreSQL instance for the main application.
    \item \textbf{Keycloak RDS Instance:} A dedicated \texttt{db.t3.micro} PostgreSQL instance for Keycloak, ensuring identity data is physically and logically isolated. For the \texttt{develop} environment, Multi-AZ is disabled to reduce costs.
    \item \textbf{AWS Secrets Manager:} This is the source of truth for all database credentials.
        \begin{itemize}
            \item Two secrets are created: \texttt{develop/rds/password} and \texttt{develop/keycloak/db/password}.
            \item Passwords are automatically generated by Terraform and stored in Secrets Manager.
            \item **Automated Rotation:** A rotation policy is configured to automatically change the passwords every 30 days, enhancing security.
            \item Applications are granted IAM permission to fetch these secrets dynamically at runtime.
        \end{itemize}
\end{itemize}
